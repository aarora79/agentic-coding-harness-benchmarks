The problem

Agentic coding burns tokens at scale

Long-horizon, not one-shot

A task is tens to hundreds of LLM turns (~50-250, up to 300+), running 10 minutes to over an hour -- not a single prompt/response.

Prefill-heavy shape

Each turn replays a growing transcript as fresh input and emits a tiny edit. Real input:output runs ~150:1 to ~660:1 -- not the ~3:1 generic pricing assumes.

Cost hides in the choices

How many turns, how much context re-read, which harness, which model -- these swing the bill several-fold for similar quality.

Organizations are already at -- or heading toward -- trillions of tokens per month, and coding agents drive a large and growing share of it. That is the bill this repo helps control.

Public leaderboards can be saturated, and generic token pricing does not reflect this workload -- you need numbers on work that looks like yours.

The cost problem

Don't read the slide - point at the bars. Both are the same width. App traffic has a fat output slice (~3:1 input:output) - that's the ratio generic pricing and leaderboards assume.

Agentic coding is wildly input-heavy: real input:output runs ~150:1 up to ~660:1, because each of ~50-250 turns replays the growing transcript. The output slice basically disappears. It's frontier-model-driven and developer-controlled, and runs 10 minutes to an hour+.

If someone asks "isn't this prefill / cache-read?" - keep them separate. "Prefill" is just the model reading the input before it generates anything, so prefill-heavy = input-heavy (what the bar shows). That is not the same as cache-read tokens: caching is a pricing feature that bills the repeated part of the input cheaper instead of recomputing it. Because coding replays a huge, mostly-repeated transcript every turn, prompt caching is exactly the lever that makes it affordable - but "how much input" and "how cheaply that input is billed" are two different axes. We kept the jargon off the slide on purpose.

Two consequences to say out loud: for app traffic the lever is route & cache the premium slice; for coding the cost hides in the harness + model choice - which is why generic pricing tells you nothing and you have to benchmark on real tasks.

Where the decision lives

Routing belongs where the context lives

Same word, two different jobs. At the gateway it is routing - a classification made on the prompt alone, which is right for application traffic. For coding the context is the repository, so the choice is decisioning: a judgement the harness can only form after it has looked around and asked. In effect the decision shifts left - out of the gateway and into the IDE, where the agentic coding harness already runs.

Follows from the input-heavy profile earlier: ~50-250 turns replaying a growing transcript, not a single self-contained request. Gateways still own the things that are stateless - rate limits, spend caps, policy.

The frontier

This answers the question a platform team always asks at this point: "we already have an LLM gateway - can't the router just live there?"

For application traffic, yes. The request is self-contained. The gateway sees one prompt, classifies it, and picks a model in milliseconds. Nothing else is needed, and that is the right place for it.

For agentic coding, no - and this follows directly from the input-heavy slide. The context is the entire repository. To know whether a task is a one-line fix or a refactor that touches twelve files, something has to open the repo, call tools, read code, and often ask the developer a clarifying question. That is a stateful judgement formed across many turns. A gateway sitting in the request path never sees any of it - by the time a prompt reaches the gateway, the decision has already had to be made.

So the naming matters: gateway-side it is routing; harness-side it is decisioning. Same intent, different amount of context required.

Land it as a shift-left move. The decision moves out of the central gateway and into the IDE, where the harness already sits next to the repo and the developer. The gateway keeps what genuinely is stateless - rate limits, spend caps, policy. That is exactly what the next slide implements.

Where it's going

Take the model choice off the developer

Task + repo → tier → frontier lookup → model · harness · effort. A swe-router skill triages the task, takes the cheapest model on the frontier that clears the bar, and escalates a tier if the result falls short.

Design: docs/vision.md · issue #161 - swe-router. Tiers: frontier / workhorse / budget, bounded escalation, every decision logged to routing.json.

The frontier

This is where the whole coding section lands. The frontier tells you which model to pick - but somebody still has to pick it, per task, and that somebody is currently a developer who would rather be writing code.

What the skill does: a router model reads the task and the repo and triages it into one of three tiers - frontier, workhorse or budget. It then consults the measured Pareto frontier and takes the cheapest non-dominated model that clears the bar for that tier. If the run fails or scores below expectation, it escalates one tier and re-runs, bounded by a maximum number of escalations. Every decision is written to routing.json, so the routing is auditable rather than magic.

Two ways to adopt it, and the order matters. Option one is advisory: the skill says loudly "switch to this model at this reasoning effort for this task," and the developer decides. Nothing is taken away from them, so there is no trust barrier - and each accepted recommendation is evidence that the routing works. Option two is autonomous: the skill spawns a headless instance of the chosen harness at the chosen model and thinking effort and just finishes the task.

Start with option one. Move to option two once developers have stopped second-guessing the pick. The frontier underneath is identical - the only thing that changes is how much of the decision the developer still carries.

The method

What is a Pareto frontier?

The set of models where no other model is both higher-scoring AND cheaper. Those are the only models worth considering. Everything else is dominated -- some frontier model beats it on both axes, so there is never a reason to pick it.

On the frontier

Non-dominated: to do better you must pay more, and to pay less you must accept a lower score. The real trade-off curve.

Dominated (skip it)

Example from our data: kimi-k2.7-code (69.98, $3.13/task) is beaten by qwen3.8-27b (78.48, $1.47/task) -- higher score and lower cost (both self-hosted). kimi-k2.7-code is off the frontier.

How to read it

Pick the quality your task needs (y-axis), then take the leftmost model on the frontier at that level -- the cheapest way to buy that quality.

Cost bases differ (metered Bedrock vs hardware-derived self-hosted), so we also draw the frontier within each hosting basis.
